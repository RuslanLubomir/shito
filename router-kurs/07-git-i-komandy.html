Git и совместная работа

Как хранить не только текущую версию файлов, а всю их историю - и как несколько человек правят один код, не затирая друг друга.

Что такое git одним предложением. Git - это программа, которая живёт рядом с твоей папкой проекта и умеет запоминать состояние всех файлов на любой момент времени, чтобы к этому моменту можно было вернуться. Ты продолжаешь работать обычным редактором; git просто ведёт журнал. В главе 6 мы его уже установили внутри WSL, так что все команды ниже даём именно из терминала Ubuntu - того же самого, где мы проверяли git --version.
Как работает тренажёр ниже. Это имитация терминала: он понимает ровно те команды, что даны в задании шага, и печатает тот текст, который git реально выводит в такой ситуации. Если набрать что-то другое - ничего не сломается, просто в этом шаге отрабатывается конкретная команда.

Зачем нужен git, если можно копировать папку

Теория. "Сохранить копию" даёт один снимок и быстро превращается в кашу из папок проект_финал, проект_финал2, проект_финал_точно. Git даёт две вещи, которых у копий нет. Первая - непрерывная история: каждая сохранённая точка помнит, что именно изменилось, когда и зачем, и к любой точке можно откатиться. Вторая - совместная работа: git умеет складывать вместе правки двух людей в одном и том же файле, если они трогали разные строки, и честно предупреждает, если трогали одну и ту же.

Пример. В проекте "Демо Банк" двое: один правит текст на странице входа, другой - расчёт процентов в другом файле. С копиями папок кто-то из них перезапишет работу другого целиком. С git каждый сохраняет свои точки, а потом их истории объединяются, и в итоговой версии есть и новый текст, и новый расчёт.
Проверь себя. Чем сохранённая точка в git отличается от копии папки с датой в названии?
ОтветКопия - это просто снимок файлов. Точка в git знает своё место в истории: от какой точки она произошла, что именно в ней изменилось построчно и какое сообщение автор к ней написал. Поэтому по истории можно двигаться, а не только "распаковать одну папку".

Первая сохранённая точка: init → status → add → commit

Теория. Четыре понятия по порядку. Репозиторий - папка, за которой git следит; создаётся командой git init (она добавляет внутрь скрытую подпапку .git, где и лежит вся история). git status показывает, что изменилось с последней точки. git add файл помечает, что именно должно попасть в следующую точку (эта "корзина отобранного" называется индекс, или staging area). git commit -m "сообщение" создаёт саму точку - коммит - из того, что отобрано.

Пример. Разберём целиком: создаём папку проекта "Демо Банк", кладём в неё файл README.md с одной строкой описания и делаем первый коммит. 
mkdir demo-bank
cd demo-bank
git init
echo "# Демо Банк" > README.md
git add README.md
git commit -m "Добавить README с описанием проекта"

Прогони эти команды в тренажёре по одной - смотри, что git отвечает на каждую.

$
Задание. По очереди: git init, затем git status, затем git add README.md, затем снова git status, затем git commit -m "Добавить README с описанием проекта".
ПодсказкаСообщение коммита пиши в кавычках целиком - без них git решит, что это несколько отдельных аргументов.
Показать разборДо add файл числится в разделе "Untracked files" - git его видит, но не отслеживает. После add он переезжает в "Changes to be committed" - отобран для точки. commit печатает короткий идентификатор точки (хеш, например a1c3f9d) и статистику: сколько файлов и строк изменилось.
Почему сообщение важнее, чем кажется. Через три месяца ты откроешь историю, чтобы найти, где сломался расчёт процентов. Двадцать коммитов с текстом fix не помогут ничем - придётся смотреть каждый. Правило простое: сообщение отвечает на вопрос "что изменится в поведении проекта", в повелительной или безличной форме: Исправить опечатку в заголовке страницы входа, а не fix, изменения, ещё раз.

История: git log --oneline

Теория. git log печатает список коммитов от новых к старым с автором и датой. Флаг --oneline сжимает каждый коммит до одной строки: короткий хеш плюс сообщение. Это самый частый способ посмотреть историю - и именно здесь видно, хорошие у тебя сообщения или нет.

Пример. После пары коммитов в "Демо Банке" история выглядит так - и по ней сразу понятно, что происходило.
$
Задание. Введи git log --oneline.
ПодсказкаДва минуса перед словом oneline, без пробела внутри.
Показать разборКаждая строка - один коммит. Первый столбец - сокращённый хеш, по нему можно ссылаться на точку в других командах. Верхняя строка - самая свежая точка.

Ветки: пробовать, не ломая рабочую версию

Теория. Ветка (branch) - это отдельная линия истории. Основную обычно зовут main. Если нужно попробовать рискованное изменение, делают новую ветку: коммиты идут в неё, а main остаётся ровно в том состоянии, в котором работал. Команды: git branch - список ветвей (звёздочка у текущей), git switch -c имя - создать новую и сразу перейти в неё, git switch main - вернуться назад, git merge имя - влить изменения ветки в текущую. (В старых инструкциях вместо switch встретится git checkout -b - это то же самое, мы дальше используем только switch.)

Пример. В "Демо Банке" хотим переписать текст на странице входа. Делаем ветку login-text, коммитим там, убеждаемся, что всё хорошо, возвращаемся в main и сливаем. Если бы не понравилось - ветку можно было просто выбросить, и main не заметил бы ничего.
$
Задание. По очереди: git branch, git switch -c login-text, git branch, git switch main, git merge login-text.
ПодсказкаСначала посмотри список ветвей, чтобы увидеть, что изначально она одна.
Показать разборgit branch в начале показывает только * main. После switch -c появляется вторая ветка и звёздочка переезжает на неё. merge в простом случае делает "fast-forward" - просто сдвигает main вперёд к коммитам ветки, потому что в main с момента ветвления ничего не менялось.
Проверь себя. Ты сделал в ветке три коммита и понял, что идея была плохая. Что произошло с main?
ОтветНичего. main стоит там же, где стоял до ветвления - пока не сделан merge, изменения живут только в ветке.

GitHub и remote: история не только на твоём компьютере

Теория. Всё выше работало полностью локально - история лежит в папке .git на твоём диске. Remote ("удалённый репозиторий") - это копия того же репозитория на сервере, обычно на GitHub. Она нужна для двух вещей: не потерять всё вместе с диском и дать другим людям доступ. git remote add origin АДРЕС один раз запоминает адрес под именем origin (это просто принятое по традиции имя, не ключевое слово). git push отправляет твои коммиты на сервер, git pull забирает оттуда чужие.

Пример. Создаём на GitHub пустой репозиторий demo-bank, копируем его адрес и связываем с локальной папкой. Флаг -u при первом пуше запоминает связь ветки main с origin/main, чтобы дальше хватало просто git push.
$
Задание. По очереди: git remote add origin https://github.com/user/demo-bank.git, git remote -v, git push -u origin main, git pull.
ПодсказкаАдрес репозитория оканчивается на .git - GitHub даёт его готовым в кнопке "Code".
Показать разборremote add ничего не печатает при успехе - это нормально для git. remote -v показывает адрес дважды: отдельно для чтения (fetch) и для записи (push). pull при отсутствии новых чужих коммитов отвечает Already up to date.

Pull request: заявка "хочу влить это в main"

Теория. Pull request (PR) - это не команда git, а страница на GitHub. Смысл: "вот моя ветка, вот построчная разница с main (её называют diff), давайте посмотрим и решим, вливать или нет". До нажатия кнопки Merge в main ничего не попадает. PR даёт три вещи: видимую разницу, место для обсуждения конкретных строк и возможность автоматических проверок кода перед слиянием.

Пример. Ветка login-text отправлена на GitHub через git push -u origin login-text. На странице репозитория появляется предложение "Compare & pull request" - нажимаешь, пишешь заголовок и пояснение, создаёшь PR, просматриваешь diff и жмёшь Merge pull request.
Честная оговорка: PR - это про командную работу, а в этом курсе ты пока один. Полезная привычка всё равно тренируется в одиночку: делай ветку, пушь её, открывай PR сам себе, перечитывай diff целиком и только потом жми Merge. Именно чтение своего же diff ловит забытые отладочные строки и случайно закоммиченные пароли. Строгий процесс с обязательным вторым проверяющим и запретом пуша прямо в main - тема отдельной главы про командную разработку; здесь всё сознательно упрощено до одного человека.

Конфликт слияния

Теория. Конфликт (merge conflict) возникает, когда две ветки изменили одни и те же строки одного файла. Git не угадывает, чья правка правильная, поэтому останавливает слияние и записывает в файл оба варианта с маркерами. Твоя задача - открыть файл, оставить нужный текст, удалить все маркеры, затем git add файл и git commit.

Пример. Внутри файла конфликт выглядит буквально так - и <<<<<<<, =======, >>>>>>> это обычный текст, добавленный git, его нужно стереть руками: 
<<<<<<< HEAD
# Демо Банк - интернет-банк для учебного проекта
=======
# Демо Банк - демонстрационный банковский сервис
>>>>>>> login-text

Сверху - версия из текущей ветки (HEAD), снизу - из вливаемой.

Прежде чем продолжить. Разрешить конфликт - значит физически открыть файл в редакторе и руками решить, что там останется: можно оставить одну из двух строк целиком, обе сразу, или написать третий вариант - и в любом случае стереть все три маркера (<<<<<<<, =======, >>>>>>>) вручную, git это за тебя не сделает.
Как может выглядеть результат Например, если решить оставить более короткую формулировку: 
# Демо Банк - демонстрационный банковский сервис
Ни одного маркера, ни одной лишней строки - именно так должен выглядеть файл, когда ты набираешь git add.
$
Задание. Введи по очереди: git merge login-text, git status, cat README.md (посмотреть файл уже после ручной правки в редакторе - представь, что ты оставил короткую версию и стёр маркеры), затем git add README.md и git commit -m "Объединить версии описания проекта".
ПодсказкаКонфликт - не ошибка и не поломка. Это вопрос от git к тебе, на который отвечают правкой файла, а не командой.
Показать разборstatus во время конфликта показывает раздел "Unmerged paths" и файл как both modified. cat README.md подтверждает, что маркеров больше нет - файл уже в том виде, в котором ты его оставил после правки. После этого git add означает "я решил конфликт в этом файле", а commit завершает слияние отдельным коммитом.

.gitignore: чему в истории не место

Теория. .gitignore - обычный текстовый файл в корне репозитория со списком шаблонов имён, которые git должен игнорировать: он перестанет предлагать их добавить и не пустит в историю случайно. Игнорируют три типа вещей: секреты (файлы с паролями и ключами), временные и служебные файлы (логи, __pycache__, .vscode/) и зависимости - скачанные библиотеки, которые в любой момент ставятся заново по списку (node_modules/).

Пример. Минимальный .gitignore для "Демо Банка": слеш в конце означает папку, звёздочка - любые символы. 
.env
*.log
node_modules/
__pycache__/
Связь с будущей главой. В главе про секреты и переменные окружения пароль от базы данных "Демо Банка" будет лежать в файле .env. Критично важно: этот файл должен попасть в .gitignore до первого коммита. Git не забывает - если пароль один раз попал в историю и уехал на GitHub, удаления файла следующим коммитом недостаточно, старая точка всё ещё его содержит, и пароль придётся считать скомпрометированным и менять.
Проверь себя. Ты закоммитил .env с паролем, запушил, заметил и следующим коммитом файл удалил. Пароль в безопасности?
ОтветНет. Коммит с паролем остался в истории и на сервере - его можно достать одной командой. Правильная реакция: сменить сам пароль, а потом уже приводить репозиторий в порядок.

Теория. Рабочий цикл, который ты будешь повторять тысячи раз: правка в редакторе → git status (убедиться, что изменилось именно то) → git add → git commit -m "...".

$
Подсказка 1Начни с git status - он покажет файл как modified и подскажет, какой командой его добавить.
Подсказка 2Тренажёр принимает сообщение Исправить опечатку в названии банка в README. Слово fix он тоже примет - но ответит замечанием.
