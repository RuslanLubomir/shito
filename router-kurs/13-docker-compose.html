Docker Compose - несколько контейнеров вместе

Один файл вместо пачки длинных docker run: приложение Демо Банка и его база поднимаются вместе и знают, как найти друг друга.

Один технический момент сразу. Команды ниже одинаковы в PowerShell на Windows 11 и в терминале Mac/Linux, если установлен Docker Desktop и он запущен (значок кита в трее не «Starting…»). Значок $ печатать не нужно - это пометка «курсор готов». Файл docker-compose.yml лежит в папке проекта, и команды набирают, находясь в этой папке. Старые инструкции пишут docker-compose через дефис - это прежняя отдельная программа. Сейчас в Docker Desktop та же идея вызывается с пробелом: docker compose.
Как работает тренажёр ниже. Это не настоящий терминал, а имитация: он понимает ровно ту команду, что дана в задании, и отвечает заранее заготовленным текстом - так же, как в реальности ответил бы Docker Compose, когда образы уже скачаны и собраны (главы 11-12). Ничего на твоём компьютере он не запускает и не удаляет. Если наберёшь что-то другое, тренажёр не сломался - в этом шаге отрабатывается конкретная команда.

Два контейнера, которые нужны одновременно

Теория. Демо Банку мало одного контейнера. Нужно приложение (свой образ из Dockerfile, глава 12) и база PostgreSQL (готовый образ, глава 11). Они должны оказаться в одной сети, чтобы приложение достучалось до базы, и база должна стартовать не позже приложения. Каждый docker run - это длинная строка флагов. Забыл флаг сети - контейнеры друг друга не видят. Забыл пароль базы - Postgres сразу завершается. Забыл том с данными - после остановки база пустая. Повторять это руками каждый запуск легко ошибиться.

Пример. Тот же Демо Банк тремя отдельными командами. Сначала общая сеть, потом база, потом приложение. Имена --name и --network надо не перепутать, а порядок - не перепутать тем более: если запустить приложение раньше базы, первое подключение не удастся. 
docker network create demobank
docker run -d --name db --network demobank -e POSTGRES_PASSWORD=demo-secret -e POSTGRES_DB=demobank -v db_data:/var/lib/postgresql/data postgres:16
docker run -d --name app --network demobank -p 8000:8000 -e DATABASE_URL=postgresql://postgres:demo-secret@db:5432/demobank demobank-app
Проверь себя. Почему здесь недостаточно просто два раза вызвать docker run без --network?
ОтветКаждый docker run без общей сети сажает контейнер в свою изолированную сеть. Имя db из приложения тогда никуда не ведёт: контейнеры не «соседи», даже если оба запущены на одном Windows.

Один файл описывает весь проект

Теория. Docker Compose читает один текстовый файл - обычно docker-compose.yml - и по нему сам создаёт сеть, тома и контейнеры. В файле перечислены сервисы проекта. Слово «сервис» здесь не то, что в главе 1. Там служба - это программа, которая работает в фоне Windows сама по себе. Здесь сервис - это просто один пункт списка: «контейнер такого-то типа с такими-то настройками». У Демо Банка в списке два сервиса: app и db.

Теория. Формат файла называется YAML. Это не язык программирования, а способ записать структуру отступами. Правило то же, что у блоков в Python (глава 9): строка, сдвинутая вправо, принадлежит строке выше. Сдвинул недостаточно - ключ стал чужим соседом, а не вложенной настройкой. Пробелы и табы лучше не смешивать; в этом курсе везде два пробела на уровень.

Пример. Мини-кусок, только чтобы увидеть отступ. image сдвинут относительно db, значит образ относится к сервису db, а не ко всему файлу. 
services:
  db:
    image: postgres:16
Проверь себя. В Python строка внутри функции пишется с отступом, иначе это уже не тело функции. Что будет аналогичной ошибкой в YAML, если пароль базы задуман как настройка сервиса db?
ОтветПароль записан на том же отступе, что и db, или сразу под ключом без дополнительного сдвига. Тогда он не вложен в db. Compose либо не передаст пароль в Postgres, либо откажется читать файл, потому что у сервиса появилось неизвестное поле.

Файл Демо Банка построчно

Теория. Ниже полный учебный файл. image - взять готовый образ (так берём Postgres). build: . - собрать образ из Dockerfile в текущей папке (так берём приложение, точка означает «эта папка»). environment - переменные окружения: настройки, которые программа читает при старте, а не зашивает в код. Для официального образа Postgres пароль обязателен, иначе контейнер сразу завершится с ошибкой. ports пробрасывает порт наружу: слева порт на твоём Windows, справа порт внутри контейнера. Базе такой проброс не нужен - к ней ходит только приложение, не браузер.

Теория. volumes - именованный том. Контейнер одноразовый: удалил контейнер - исчезла его внутренняя файловая система. Том - отдельное хранилище Docker, как флешка, которую не выбрасывают вместе с коробкой. Строка db_data:/var/lib/postgresql/data говорит: флешку с именем db_data подключить в то место внутри контейнера, где Postgres держит файлы базы. Путь слева от двоеточия в этом виде - имя тома, не папка на диске C:. Путь справа - путь внутри Linux-контейнера, его не надо переписывать в стиль Windows.

Пример. Папка проекта на диске называется demobank. От этого имени Compose потом назовёт контейнеры и том. Файл целиком: 
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: demo-secret
      POSTGRES_DB: demobank
    volumes:
      - db_data:/var/lib/postgresql/data

  app:
    build: .
    ports:
      - "8000:8000"
    depends_on:
      - db
    environment:
      DATABASE_URL: postgresql://postgres:demo-secret@db:5432/demobank

volumes:
  db_data:

Теория. depends_on задаёт порядок: сервис app зависит от сервиса db, поэтому Compose сначала запускает контейнер базы, потом контейнер приложения. Нижний ключ volumes: на том же уровне, что и services:, объявляет том db_data. Без этого объявления имя в секции db было бы ссылкой в никуда.

Честная оговорка. depends_on ждёт только того, что контейнер db запущен, а не того, что PostgreSQL уже принимает подключения. После старта контейнера база ещё несколько секунд инициализируется. Учебный файл показывает порядок «сначала база», но одной этой строчки мало: настоящее приложение Демо Банка должно повторить попытку подключения, если первая не удалась. Иначе редкий быстрый старт будет выглядеть как «база сломалась», хотя она просто ещё не готова.
Проверь себя. Что произойдёт со счетами Демо Банка, если у db убрать volumes, затем остановить проект и поднять его снова?
ОтветБаза будет пустой. Файлы Postgres жили только внутри удалённого контейнера. Том как раз для того, чтобы они пережили удаление контейнера.

Внутри проекта друг друга зовут по имени сервиса

Теория. Compose сам создаёт сеть проекта и записывает в ней имена сервисов. Из контейнера app имя db - это адрес контейнера базы, порт 5432. Поэтому в строке подключения написано @db:5432, а не @localhost. localhost всегда значит «я сам». Внутри контейнера приложения «я сам» - это приложение, а не база и не твой Windows. В браузере на Windows ты открываешь localhost:8000, потому что порт 8000 проброшен наружу. База наружу не проброшена, с Windows по имени db к ней не зайти - это имя существует только в сети Compose.

Пример. Одна и та же база, два разных адреса. Приложение в контейнере: postgresql://postgres:demo-secret@db:5432/demobank. Браузер на Windows, если бы порт базы пробросили (в нашем файле мы этого не делаем): localhost и тот порт, что стоит слева в ports. Путаница «пишу localhost, как в браузере» - самая частая причина ошибки «connection refused» в первый день с Compose.
Проверь себя. Приложение Демо Банка не может подключиться к базе, в логе «connection refused» на localhost:5432. Файл при этом поднимает оба контейнера. Что исправить в DATABASE_URL?
ОтветЗаменить localhost на имя сервиса db. Из контейнера приложения localhost - это он сам, Postgres там не слушает.

Поднять, посмотреть, прочитать логи

Теория. docker compose up создаёт недостающее и запускает все сервисы из файла. Без флага -d терминал остаётся приклеен к логам, пока не нажмёшь Ctrl+C (это остановит и контейнеры). docker compose up -d делает то же самое и сразу возвращает приглашение: -d значит detached, «в фоне». docker compose ps показывает контейнеры этого проекта, не все контейнеры Docker на машине. docker compose logs печатает логи всех сервисов и завершается. docker compose logs -f не завершается, а следит за новыми строками, пока не прервёшь. docker compose logs db - только один сервис. В тренажёрах ниже слежки нет: имитация должна закончиться и вернуть курсор, как обычная команда без -f.

Пример. Считаем, что образ postgres:16 уже скачан в главе 11, а образ приложения уже собран. Папка проекта - demobank, поэтому в выводе имена demobank-db-1 и demobank-app-1. Первый запуск создаёт сеть demobank_default. Время в настоящем выводе будет другим, набор строк - тот же.
Задание. Подними проект в фоне: docker compose up -d
$
ПодсказкаНужны три слова и флаг: compose, действие up, и -d. Без -d это другая команда, тренажёр этого шага ждёт фоновый запуск.
Показать разборCompose создал сеть проекта и запустил оба контейнера. Галочки - это отчёт «сделано», не меню. Приглашение вернулось, потому что был флаг -d: контейнеры работают, а терминал свободен.
Задание. Посмотри, что сейчас запущено в этом проекте: docker compose ps
$
ПодсказкаДва слова: docker compose ps. Это не docker ps - та команда показала бы все контейнеры машины, а не только проект из текущего файла.
Показать разборОба сервиса в статусе Up. У app в колонке PORTS есть 0.0.0.0:8000->8000/tcp - порт открыт на Windows. У db только 5432/tcp без стрелки наружу: порт виден соседним контейнерам в сети Compose, но не браузеру. Колонка COMMAND у базы обрезана многоточием - так Compose укорачивает длинную команду старта, это не ошибка.
Задание. Прочитай уже накопленные логи обоих сервисов: docker compose logs
Пример того, что считается честным выводом. Строки с префиксом db-1 - типичные сообщения самого PostgreSQL и его скрипта первого запуска (том ещё пустой, поэтому база инициализируется, а не пропускает инициализацию). Дата, номер процесса и точная версия патча в живом Docker будут другими. Строки app-1 - то, что печатает программа Демо Банка; Compose только дописывает имя сервиса слева. Команда без -f печатает накопленное и заканчивается.
$
ПодсказкаИменно docker compose logs, без -f и без имени сервиса - в этом шаге смотрим оба сразу.
Показать разборПрефикс db-1 / app-1 Compose добавляет сам, чтобы логи двух контейнеров не смешались в кашу. Строка Postgres «database system is ready to accept connections» значит, что база уже слушает. Строка приложения про db:5432 значит, что оно нашло базу по имени сервиса, а не по localhost. Если бы приложения стартовало раньше готовности Postgres, здесь была бы ошибка подключения - это как раз дыра, о которой предупреждал depends_on.

Остановить проект и не снести базу случайно

Теория. docker compose down останавливает и удаляет контейнеры этого проекта и его сеть. Именованные тома он не трогает. Следующий up создаст новые контейнеры и подключит ту же «флешку» - счета Демо Банка на месте. Это поведение по умолчанию, отдельный флаг для «сохрани данные» не нужен.

Задание. Останови проект без удаления данных: docker compose down
$
ПодсказкаБез -v и без -d. -d относится к up, не к down.
Показать разборВ отчёте есть Container Removed и Network Removed. Строки Volume Removed нет - том demobank_db_data остался. Имя тома Compose собирает из имени папки проекта и имени тома в файле.
Честное предупреждение, до команды. docker compose down -v удаляет и тома проекта. Для Демо Банка это значит: учебные счета и операции исчезнут безвозвратно. Команда не спрашивает «ты уверен?». Флаг короткий, его легко дописать по привычке из чужой инструкции «чтобы очистить всё». Очистить контейнеры и очистить данные - разные действия. Тренажёр ниже ничего на диске не сотрёт, но вывод покажет ту строку, из-за которой новички теряют базу.
Задание. Посмотри, чем опасный вариант отличается в отчёте. Введи именно docker compose down -v - только в тренажёре.
$
ПодсказкаТе же два слова, что в прошлом задании, плюс флаг -v. На своём компьютере эту форму не используй, пока сознательно не хочешь пустую базу.
Показать разборПоявилась строка Volume Removed для demobank_db_data. Именно она означает потерю файлов Postgres. Без -v этой строки не было. Контейнеры и сеть удаляются в обоих случаях; данные тома - только с -v.
Проверь себя. Хочешь остановить Демо Банк на ночь и завтра продолжить с теми же учебными счетами. Какая команда?
Ответdocker compose down без -v. Завтра снова docker compose up -d - том подключится к новому контейнеру базы.

Найди ошибки в чужом файле

Теория. Файл ниже похож на рабочий, но Демо Банк с ним не поднимется как задумано. Ошибок две: одна про отступы YAML, вторая про порядок старта. Сеть и адрес db в строке подключения здесь уже правильные - не «чини» то, что не сломано. 

services:
  db:
    image: postgres:16
    environment:
    POSTGRES_PASSWORD: demo-secret
    POSTGRES_DB: demobank
    volumes:
      - db_data:/var/lib/postgresql/data

  app:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql://postgres:demo-secret@db:5432/demobank

volumes:
  db_data:
Задание. Найди обе ошибки и сформулируй, как должен выглядеть исправленный фрагмент. Сверься с разбором только после своей версии.
ПодсказкаСравни отступ POSTGRES_PASSWORD с отступом image и с рабочим файлом выше. Ключ environment без вложенных строк не передаёт Postgres ничего. Вторая ошибка - про то, чего в сервисе app нет, хотя в разобранном файле было.
Подсказка ещёCompose проверяет схему файла. Поле, которое стоит на уровне сервиса и не входит в список известных ключей, он отвергает. Пароль должен быть внутри environment, сдвинутый ещё на один уровень. Порядок старта задаёт depends_on.
Показать разбор

POSTGRES_PASSWORD и POSTGRES_DB стоят на том же отступе, что и environment, поэтому они не внутри него, а рядом - как неизвестные поля сервиса db. Такой файл Compose не принимает: дополнительное свойство POSTGRES_PASSWORD у сервиса не разрешено. Даже если бы принял, официальный образ не увидел бы пароль и завершился. Нужен сдвиг, как у вложенного блока в Python:

    environment:
      POSTGRES_PASSWORD: demo-secret
      POSTGRES_DB: demobank

Вторая ошибка: у app нет depends_on. Контейнер приложения может стартовать раньше контейнера базы. Это не замена повторам подключения в коде, но порядок «сначала db» в файле должен быть:

    depends_on:
      - db

Строка @db:5432 и том db_data здесь уже верные, их менять не надо.

  • отличить image от build и объяснить, зачем базе именованный том
