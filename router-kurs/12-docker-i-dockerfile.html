Docker и Dockerfile

В прошлой главе базу данных запустили одной длинной командой и не разбирались, что это было. Теперь разберёмся - и упакуем в коробку свой собственный код.

Один технический момент сразу. Ты на Windows 11, значит Docker у тебя - это Docker Desktop (та самая программа с иконкой китёнка, которую ставили в главе 11). Команды docker ... печатаются в обычном терминале Windows - PowerShell или в терминале внутри редактора кода, - и они одинаковые на Windows, Mac и Linux. Значок $ в примерах ниже - только пометка "здесь курсор ждёт команду", печатать его не надо. Ещё одно: пока Docker Desktop не запущен (иконка в трее серая или его нет), любая команда docker ответит ошибкой соединения - это не поломка, просто движок выключен.
Как работает тренажёр ниже. Это имитация терминала: он понимает ровно ту команду, что дана в задании, и печатает тот текст, который в этой ситуации напечатал бы настоящий Docker. Наберёшь что-то другое - тренажёр не сломался, просто в этом шаге отрабатывается конкретная команда.

Зачем вообще коробка: "у меня работает, а на сервере - нет"

Теория. Программа никогда не работает "сама по себе" - ей нужно окружение: нужная версия языка (например, Python 3.12, а не 3.9), нужные версии библиотек, нужные системные файлы. На твоём ноутбуке это окружение сложилось само, за месяцы установок. На арендованном сервере его нет и оно другое. Отсюда классика: код, который безупречно работает у тебя, на сервере падает с непонятной ошибкой. Docker решает это грубо и эффективно: он позволяет упаковать в одну коробку (контейнер) вообще всё, что нужно для запуска - сам код, интерпретатор Python, все библиотеки, нужные системные пакеты. Коробку переносишь на сервер, и она запускается там точно так же, как у тебя, потому что внутри неё всё то же самое.

Пример. В проекте Демо Банка бэкенд написан под Python 3.12 и использует библиотеку, которая появилась только в свежих версиях. На сервере, который мы арендовали, "из коробки" стоит Python 3.10. Без Docker пришлось бы вручную ставить на сервер второй Python, следить, чтобы он не конфликтовал с системным, повторять это на каждом новом сервере. С Docker в коробке лежит ровно python:3.12-slim, и что стоит на самом сервере - уже не важно.
Проверь себя. Коллега говорит: "Я скинул тебе код, почему у тебя не запускается, у меня же работает". Что именно он не передал вместе с кодом?
ОтветОкружение: версию Python, набор установленных библиотек и их версии, системные пакеты. Код - это только часть того, что нужно для запуска. Контейнер передаётся вместе с окружением, поэтому такой разговор просто не возникает.

Образ и контейнер - это разные вещи

Теория. Образ (image) - это неизменяемый заготовленный слепок: рецепт вместе со всеми ингредиентами, уже сложенными в правильном порядке. Сам по себе он ничего не делает, он просто лежит на диске. Контейнер (container) - это запущенный по этому образу живой экземпляр: процесс, который работает, что-то печатает, занимает память и порт. Из одного образа можно запустить сколько угодно контейнеров одновременно, и они друг о друге ничего не знают. Удалить контейнер - не значит потерять образ: образ остался, из него запускают новый контейнер за секунду.

Пример. Образ postgres:16 из главы 11 ты скачал один раз. Из него можно поднять два контейнера: один - база для разработки на порту 5432, второй - отдельная чистая база для тестов на 5433. Один и тот же "чертёж", два независимых работающих экземпляра с разными данными внутри.
Проверь себя. Ты сделал docker rm у контейнера с базой. Нужно ли теперь снова качать PostgreSQL из интернета, чтобы поднять базу заново?
ОтветНет. Удалён был контейнер, а образ postgres:16 остался на диске - docker run поднимет новый контейнер сразу, без скачивания. (Данные внутри удалённого контейнера, если они не были сохранены наружу, при этом потеряны - об этом будет отдельно в главе про тома.)

Четыре команды, которыми пользуешься каждый день

Теория. docker ps - список работающих сейчас контейнеров (с флагом -a - включая остановленные и упавшие). docker images - какие образы лежат у тебя на диске и сколько места занимают. docker stop <имя-или-id> - вежливо остановить контейнер, docker rm <имя-или-id> - удалить уже остановленный. docker logs <имя-или-id> - показать всё, что контейнер напечатал в консоль за свою жизнь; это главный инструмент отладки, потому что контейнер печатает не в твоё окно, а "внутрь себя".

Разобранный пример. У каждого контейнера есть длинный шестнадцатеричный ID и имя (своё, заданное через --name, или случайное смешное вроде nostalgic_turing). В командах можно указывать и то и другое, причём от ID хватает первых нескольких символов - лишь бы они однозначно указывали на один контейнер.

$
Задание. Посмотри, что сейчас запущено: docker ps. Потом посмотри список образов: docker images.
ПодсказкаДве команды по очереди, каждая - Enter. Обрати внимание: в docker ps столбец PORTS показывает, какой порт контейнера выведен наружу, а столбец STATUS - как давно он работает.
Показать разборdocker ps показал один работающий контейнер demobank-db из образа postgres:16 - тот самый из главы 11, он живёт уже два часа и слушает порт 5432. docker images показал два образа на диске: postgres:16 (432 МБ) и python:3.12-slim (130 МБ). Образов больше, чем контейнеров - это нормально, образ может просто лежать без дела.

Dockerfile - рецепт своего образа, построчно

Теория. Dockerfile - это текстовый файл без расширения, который лежит в корне проекта и по шагам описывает, как собрать образ: от какой готовой основы отталкиваемся, что внутрь скопировать, что установить, что запускать при старте. Каждая строка - один шаг. Docker выполняет их сверху вниз и получает образ. 

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "app.py"]

Что делает каждая строка.
FROM python:3.12-slim - берём за основу готовый официальный образ с Python 3.12. Слово slim означает урезанную сборку: тот же Python, но без кучи лишних системных пакетов, поэтому образ в разы меньше.
WORKDIR /app - создаём внутри коробки папку /app и делаем её текущей. Все следующие команды выполняются "находясь" в ней. Это просто чтобы код не валялся в корне.
COPY requirements.txt . - копируем из своей папки на компьютере в коробку (в /app, точка = "сюда") только один файл: список нужных библиотек.
RUN pip install -r requirements.txt - внутри коробки устанавливаем эти библиотеки. RUN - это "выполни команду во время сборки, один раз".
COPY . . - теперь копируем внутрь всё остальное: сам код проекта.
CMD ["python", "app.py"] - что запустить, когда из этого образа поднимут контейнер. В отличие от RUN, эта строка при сборке не выполняется - она запоминается "на потом".

Почему requirements.txt копируется отдельно и раньше кода. Docker запоминает результат каждой строки отдельно - это называется слои, а повторное использование уже готовых слоёв - кэширование. При новой сборке Docker идёт по строкам сверху вниз и, пока входные данные строки не изменились, берёт готовый результат с прошлого раза мгновенно. Как только доходит до изменившейся строки - её и все следующие выполняет заново. Ты правишь код в сто раз чаще, чем список библиотек. Если бы стояло COPY . . перед установкой, то любая правка одной буквы в коде "ломала" бы кэш и pip install шёл бы заново каждую сборку - это минуты ожидания. А при таком порядке правка кода задевает только две последние строки, и сборка занимает пару секунд.

Пример. В Демо Банке requirements.txt меняется примерно раз в неделю, код - двадцать раз в день. Именно этот порядок строк превратил пересборку с 90 секунд в 3 секунды - разница, из-за которой начинаешь пересобирать спокойно, а не откладывать.
Проверь себя. Чем RUN отличается от CMD?
ОтветRUN выполняется один раз во время сборки образа, и его результат остаётся внутри образа (установленные библиотеки). CMD при сборке не выполняется вообще - это запись "какую команду запустить при старте контейнера", она срабатывает на docker run.

Собираем образ

Теория. docker build -t demobank-app . - собрать образ по Dockerfile. -t demobank-app - дать образу человеческое имя (tag), иначе он останется безымянным и найти его будет неудобно. Последняя точка - это не опечатка и не конец предложения: это путь к папке, содержимое которой отправляется Docker'у как исходники для сборки (контекст сборки). Точка = "текущая папка". Именно в ней Docker ищет Dockerfile и оттуда берёт файлы для COPY.

$
Задание. Собери образ: docker build -t demobank-app .
ПодсказкаНе забудь пробел и точку в конце - без них Docker не поймёт, где брать файлы, и ответит ошибкой про отсутствие контекста.
Показать разборDocker вывел строки со словом CACHED - это те шаги, результат которых он взял с прошлой сборки (установка библиотек в том числе, потому что requirements.txt не менялся). Заново выполнились только копирование кода и финальная упаковка. В конце - строка о том, что образ получил имя demobank-app:latest. Слово latest Docker дописывает сам, когда версия не указана явно.

Запускаем и прокидываем порт

Теория. Контейнер изолирован от твоего компьютера - у него как бы своя маленькая отдельная сеть. Если программа внутри слушает порт 8000, снаружи по адресу localhost:8000 её всё равно не видно: изнутри наружу дверей нет по умолчанию. Дверь открывают флагом -p: -p 8000:8000 читается как "порт 8000 моего компьютера соединить с портом 8000 внутри контейнера". Слева всегда твой компьютер, справа - контейнер, и они могут не совпадать: -p 9000:8000 означает "я захожу на localhost:9000, а попадаю на 8000 внутри".

Пример. Порт 8000 на ноутбуке уже занят чем-то другим - вместо того чтобы искать и убивать ту программу, запускаем docker run -p 8080:8000 demobank-app и открываем http://localhost:8080. Внутри контейнера при этом ничего менять не пришлось.
$
Задание. Запусти: docker run -p 8000:8000 demobank-app
ПодсказкаПосле запуска окно терминала "залипнет" - контейнер работает и печатает в него. Это нормально, так и должно быть. Остановить - Ctrl+C.
Показать разборПриложение написало, что слушает 0.0.0.0:8000 - адрес 0.0.0.0 внутри контейнера значит "принимаю подключения с любого адреса", и это важно: если бы программа слушала только 127.0.0.1, то снаружи она была бы недоступна даже с проброшенным портом. Терминал остался занят - контейнер запущен в переднем плане. Чтобы отпустить терминал, запускают с флагом -d (detached, в фоне).

Контейнер упал сразу после старта - не гадай, читай логи

Теория. Самая частая история новичка: docker run -d прошёл, выдал ID, а через секунду docker ps пустой. Это значит, что программа внутри запустилась, упала с ошибкой, и контейнер честно завершился - контейнер живёт ровно столько, сколько живёт его главный процесс. Причина ошибки не пропала: она напечаталась внутрь контейнера. Показать её: docker ps -a (чтобы найти ID упавшего) и затем docker logs <id>.

$
Задание. Найди упавший контейнер: docker ps -a, затем прочитай причину: docker logs 4f1c9a2b7d3e
ПодсказкаВ docker ps -a смотри столбец STATUS: Exited (1) означает, что процесс внутри завершился с ошибкой. Ноль в скобках - завершился нормально.
Показать разборВ логах - обычная трассировка Python: FileNotFoundError на config.yml. То есть код внутри контейнера ищет файл настроек, которого в образ не попало. Причина почти всегда одна из двух: файл исключён в .dockerignore, или он вообще не лежит в папке, из которой собирался образ. Заметь: без docker logs ты бы видел только "контейнер не работает" и мог бы час перебирать варианты.

Останавливаем и убираем за собой

Теория. docker stop <id> посылает программе внутри сигнал "заканчивай работу" и даёт несколько секунд на корректное завершение. Остановленный контейнер никуда не исчезает - он остаётся в списке docker ps -a и занимает место на диске, поэтому после него делают docker rm <id>. Удалить работающий контейнер обычной rm нельзя - Docker не даст, сначала останови.

$
Задание. Останови: docker stop demobank-db, потом удали: docker rm demobank-db. Для интереса попробуй сначала удалить работающий: docker rm demobank-db до остановки - и посмотри на ответ.
ПодсказкаОбе команды печатают в ответ просто имя контейнера - это и есть подтверждение, что всё получилось. Docker вообще скуп на слова, когда всё хорошо.
Показать разборПопытка удалить работающий контейнер даёт ошибку с прямой подсказкой "Stop the container before removing" - Docker специально не позволяет снести то, что прямо сейчас работает. После stop та же rm проходит молча. Образ postgres:16 при этом на диске остался - проверяется через docker images.

.dockerignore - тот же принцип, что и .gitignore

Теория. Помнишь .gitignore из главы 7 - список того, что не надо отправлять в репозиторий? У Docker есть ровно такой же по смыслу файл .dockerignore: список того, что не надо отправлять в сборку образа. Он важен, потому что COPY . . буквально означает "копируй всё", и без фильтра в коробку уедут папка виртуального окружения .venv (сотни мегабайт, причём собранные под Windows и внутри Linux-контейнера всё равно нерабочие), вся история .git, кэш __pycache__ и локальный файл с паролями .env. Последнее - уже не только про размер, но и про безопасность: образ можно кому-то передать. 

.venv/
.git/
__pycache__/
*.pyc
.env
node_modules/
Пример. Первая сборка образа Демо Банка получилась 1.4 ГБ и собиралась минуту с лишним - Docker покорно упаковал внутрь .venv и .git. После добавления шести строк выше образ стал 180 МБ. Ничего в коде не менялось.
Проверь себя. Почему исключить .venv - это не потеря библиотек, ведь программе внутри контейнера они нужны?
ОтветПотому что библиотеки внутрь образа попадают не копированием папки, а установкой заново строкой RUN pip install -r requirements.txt - уже внутри Linux-контейнера и под нужную версию Python. Твоя локальная .venv там не только не нужна, но и не работоспособна.
Честная оговорка про упрощение. Всё в этой главе - один образ, один контейнер, одна команда вручную на своём компьютере. В реальном проекте Демо Банка контейнеров несколько (приложение + база + веб-сервер), их не запускают по одному руками, а описывают одним файлом и поднимают вместе - это следующая глава про Docker Compose. Дальше по курсу появится ещё два слоя, которые здесь сознательно вынесены за скобки: сохранение данных вне контейнера (сейчас, если удалить контейнер с базой, данные пропадут - в реальности так делать нельзя) и то, что один сервер обслуживает не тебя одного, а несколько независимых клиентов, и тогда изоляция контейнеров перестаёт быть удобством и становится требованием. Ничего из написанного здесь не переучивать - оно просто пока не полное.

Практика: напиши свой Dockerfile

Теория. Лучший способ закрепить - собрать образ для скрипта из четырёх строк, без фреймворков и портов. Создай на компьютере пустую папку, а в ней файл app.py: 

import requests

r = requests.get("https://api.github.com")
print("статус ответа:", r.status_code)
print("готово")

И рядом файл requirements.txt с одной строкой:

requests==2.32.3
Задание. Напиши в этой же папке Dockerfile, который: берёт за основу Python 3.12 slim, работает в папке /app, ставит библиотеки из requirements.txt (так, чтобы правка app.py не вызывала переустановку), копирует код и при старте запускает app.py. Потом собери его под именем hello-docker и запусти.
Подсказка 1Строк будет шесть, все ключевые слова пишутся заглавными: FROM, WORKDIR, COPY, RUN, COPY, CMD. Порядок важен именно из-за кэширования.
Подсказка 2Собрать: docker build -t hello-docker . (точка в конце обязательна). Запустить: docker run hello-docker - флаг -p тут не нужен, скрипт ничего не слушает, он только сам куда-то ходит и печатает.
Подсказка 3Если Docker ругается failed to read dockerfile - скорее всего Windows сохранил файл как Dockerfile.txt. Имя должно быть ровно Dockerfile, без расширения; в Проводнике включи показ расширений и убери .txt.
Показать решение Dockerfile: 
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "app.py"]
Затем: 
docker build -t hello-docker .
docker run hello-docker
В выводе запуска увидишь две строки, которые печатает сам скрипт: статус ответа: 200 и готово. После этого контейнер завершится сам - программа закончилась, значит и контейнеру жить больше незачем. Он останется в docker ps -a со статусом Exited (0): ноль означает "завершился без ошибки". Чтобы контейнер удалялся автоматически сразу после завершения, запускают docker run --rm hello-docker.
