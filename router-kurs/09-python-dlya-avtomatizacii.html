Python-скрипты для автоматизации

Не язык программирования целиком, а тот минимум, которым в реальной работе пишут маленькие скрипты: проверить, сгенерировать, запустить чужую команду и прочитать её ответ.

Честная оговорка про объём. Это не курс «Python с нуля до бэкенда» - такой курс отдельный и гораздо длиннее. Здесь берём только то, что понадобится дальше в проекте «Демо Банк»: скрипт проверки, скрипт генерации тестовых данных, скрипт, который сам дёргает docker и git. Поэтому многое из настоящего Python (классы, исключения во всех тонкостях, асинхронность, типизация) здесь сознательно не разбирается - это не «весь Python», а рабочий минимум. Если позже потребуется больше - добавим по месту, когда станет понятно, зачем.
Напоминание про тренажёр. Терминалы в этой главе - имитация: они понимают ровно команду из задания и печатают тот вывод, который реальная команда действительно даёт. Работать предполагается внутри WSL2 (Ubuntu), который ты поставил в главе 6 - то есть в том же окне терминала, где ты в главе 8 разбирался с правами и пайпами, а не в PowerShell.

1. Есть ли Python и почему он python3

Теория. В Ubuntu (а значит и в твоём WSL2) Python обычно уже установлен - его использует сама система, поэтому отдельно ставить чаще всего не нужно. Важная деталь: команда называется python3, а не python. Исторически python означал старую вторую версию языка, и чтобы никто случайно не запустил не то, в Ubuntu команду python по умолчанию просто не делают. Проверка наличия - флаг --version: почти любая консольная программа понимает его и печатает свою версию.

Пример. Если ответ выглядит как Python 3.12.3 - всё есть, ставить ничего не надо. Если вместо версии вылезает command not found - Python ставят пакетным менеджером из главы 8: sudo apt update && sudo apt install python3.
$
Задание. Проверь версию: python3 --version
ПодсказкаДва дефиса перед словом version, без пробела между ними.
Показать разборКоманда печатает одну строку - имя и номер версии. Точный номер у тебя может быть другим (3.10, 3.11, 3.12) - это нормально, для наших скриптов любая версия 3.8 и выше подойдёт.

2. venv - отдельная полка для каждого проекта

Теория. Скриптам часто нужны сторонние библиотеки - чужой готовый код, который ставится отдельно. Если ставить всё «в систему», то через полгода один проект потребует старую версию библиотеки, другой новую, и они начнут мешать друг другу. Поэтому для каждого проекта делают виртуальное окружение (venv) - отдельную папку, в которой лежит свой Python и свои библиотеки только этого проекта. Аналогия: не одна общая свалка книг на полу, а отдельная полка под каждый проект, и на каждой полке ровно нужные книги.

Пример. Команда python3 -m venv .venv создаёт в текущей папке скрытую папку .venv (точка в начале имени в Linux означает «скрытый»). Сама команда при успехе не печатает ничего - это нормально: в Unix молчание значит «сделано без ошибок». Дальше окружение надо «включить» командой source .venv/bin/activate - после этого в начале строки приглашения появляется (.venv), и слова python и pip начинают означать «тот, что на этой полке». Выключить - deactivate. Папку .venv в git не кладут - её добавляют в .gitignore (глава 7), потому что она восстанавливается одной командой.
$
Задание. Введи по очереди: python3 -m venv .venv, затем source .venv/bin/activate, затем which python.
Подсказка-m означает «запусти встроенный модуль по имени», а .venv - это просто имя папки, которую создадут. which из главы 8 показывает, какой именно файл запустится по этому имени.
Показать разборПервая команда молчит - окружение создано. Вторая тоже молчит, но меняет приглашение на (.venv) $. Третья доказывает, что подмена сработала: путь ведёт не в /usr/bin/python3, а внутрь папки проекта - значит, все библиотеки теперь будут ставиться туда.
Проверь себя. Ты удалил папку .venv. Потерян ли твой код?
ОтветНет. В .venv лежат только скачанные библиотеки и копия интерпретатора - твои .py файлы лежат рядом, в самой папке проекта. Окружение пересоздаётся двумя командами (создать + установить из requirements.txt), поэтому его и не хранят в git.

3. Синтаксис по минимуму: переменные, условия, циклы

Теория. Переменная - это имя, к которому «привязано» значение: name = "Демо Банк". Тип объявлять не нужно, Python сам понимает, что это текст (строка) или число. Условие - слово if: выполнить блок, только если проверка верна. Цикл - слово for: выполнить блок по одному разу для каждого элемента списка. Главная особенность языка: блок обозначается не скобками, а отступом (принято 4 пробела) - если отступ сбит, программа либо не запустится, либо сделает не то.

Пример. Все три вещи сразу, и это уже осмысленный скрипт: 
balance = 1500          # число
limit = 1000
if balance > limit:
    print("баланс выше лимита")
else:
    print("баланс ниже лимита")

accounts = ["Иванов", "Петрова", "Сидоров"]
for acc in accounts:
    print("клиент:", acc)
Строка с # - комментарий, Python её игнорирует. print печатает в терминал. Запускается это так: сохранить в файл demo.py и выполнить python3 demo.py.
Проверь себя. Что напечатает код выше, целиком и по строкам?
Ответбаланс выше лимита, затем клиент: Иванов, клиент: Петрова, клиент: Сидоров. Ветка else не выполняется вообще - 1500 больше 1000, так что вторая половина условия пропускается.

4. Функции - чтобы не писать одно и то же дважды

Теория. Функция - кусок кода, которому дали имя, чтобы вызывать его сколько угодно раз с разными данными. Объявляется словом def, получает аргументы в скобках и может вернуть результат словом return. Смысл ровно один и очень практичный: логика описана в одном месте, и если её надо поправить - правишь одну строку, а не десять копий, разбросанных по файлу.

Пример. Проверка суммы перевода, вынесенная в функцию: 
def check_amount(amount):
    if amount <= 0:
        return "сумма должна быть больше нуля"
    if amount > 100000:
        return "превышен лимит перевода"
    return "ок"

print(check_amount(500))
print(check_amount(-10))
print(check_amount(250000))
Напечатает: ок, сумма должна быть больше нуля, превышен лимит перевода. Обрати внимание: return не просто выдаёт значение, он сразу же прекращает работу функции - до следующих проверок дело не доходит.

5. Файлы: прочитать и записать

Теория. Файл открывают функцией open, указав путь и режим: "r" - читать, "w" - писать с нуля (внимание: старое содержимое затирается), "a" - дописывать в конец. Пишут это через конструкцию with ... as f: - она гарантирует, что файл закроется сам, даже если внутри случится ошибка. Забытый открытый файл - классическая причина «я записал, а в файле пусто»: данные ещё не успели уйти на диск.

Пример. Записать строку и тут же прочитать файл обратно: 
with open("log.txt", "a", encoding="utf-8") as f:
    f.write("резервная копия сделана\n")

with open("log.txt", "r", encoding="utf-8") as f:
    for line in f:
        print(line.strip())
\n - перевод строки, без него всё склеится в одну. encoding="utf-8" обязательно указывать при русском тексте. strip() убирает лишний перевод строки с конца, иначе print добавит второй и получатся пустые строки.
Проверь себя. Ты хотел вести журнал бэкапов и запустил скрипт с режимом "w" десять раз. Сколько строк в файле?
ОтветОдна. Режим "w" каждый раз создаёт файл заново и затирает предыдущее. Для журнала нужен "a" - дописывание в конец.

6. subprocess - скрипт, который сам вызывает команды

Теория. Вот здесь Python и становится инструментом автоматизации. Модуль subprocess позволяет из скрипта запустить любую консольную команду - docker, git, df - и получить обратно её вывод и код возврата. Код возврата (returncode) - то самое число из главы 8: 0 значит «получилось», любое другое - «ошибка». То есть скрипт может не просто запускать команды, а принимать решения по их результату: сделал бэкап - проверил код - если не ноль, записал в журнал и оповестил.

Пример. Спросить у git текущую ветку и разобрать ответ: 
import subprocess

result = subprocess.run(
    ["git", "branch", "--show-current"],
    capture_output=True, text=True
)

print("код возврата:", result.returncode)
print("ветка:", result.stdout.strip())
Команда передаётся списком слов, а не одной строкой - так безопаснее и не надо думать про кавычки и пробелы в путях. capture_output=True означает «не печатай вывод на экран, отдай его мне в переменную», text=True - «отдай текстом, а не набором байтов». В result.stdout попадает обычный вывод, в result.stderr - поток ошибок (тоже из главы 8).
Проверь себя. Скрипт выполнил docker ps, и result.returncode оказался равен 1, а result.stdout пустой. Где искать объяснение?
ОтветВ result.stderr - сообщения об ошибках уходят туда, а не в stdout. Скорее всего там будет текст про то, что демон Docker не запущен.

7. pip и requirements.txt

Теория. pip - установщик сторонних библиотек Python. При включённом venv он кладёт их на «полку» проекта. Но одной установки мало: нужен ещё файл со списком того, что проекту требуется, чтобы другой человек или сервер получили ровно такой же набор. Этот файл по традиции называется requirements.txt, его кладут в git, и восстановление окружения на новой машине превращается в одну команду pip install -r requirements.txt.

Пример. Установка библиотеки requests (её используют, чтобы скрипт мог обращаться к сайтам и API по сети) и фиксация списка. pip freeze печатает всё установленное с точными версиями, а > из главы 8 перенаправляет этот вывод в файл вместо экрана.
$
Задание. По очереди: pip install requests, затем pip freeze > requirements.txt, затем cat requirements.txt.
ПодсказкаВторая команда ничего не печатает - весь вывод ушёл в файл. Убедиться, что он там, помогает третья.
Показать разборВ файле оказались не только requests, но и его собственные зависимости - библиотеки, которые нужны уже ему самому. Это нормально и даже полезно: зафиксированы точные версии всей цепочки, значит на сервере соберётся то же самое, а не «похожее».

8. Собираем полезный скрипт из кусочков

Теория. Настоящий скрипт автоматизации почти всегда устроен одинаково: собрать факты (файл/диск/ответ команды) → сравнить с ожиданием (условие) → сказать человеку понятным текстом и вернуть код возврата. Последнее важно: если скрипт при проблеме завершается ненулевым кодом, его можно поставить в расписание или в автоматическую проверку, и о поломке узнают без чтения логов глазами.

Пример. Проверка, что бэкап существует и на диске есть место: 
import os
import shutil
import sys

BACKUP = "/home/user/backups/demo-bank.sql"
MIN_FREE_GB = 2

if os.path.exists(BACKUP):
    size_mb = os.path.getsize(BACKUP) / 1024 / 1024
    print(f"бэкап найден, размер {size_mb:.1f} МБ")
else:
    print("бэкапа нет!")
    sys.exit(1)

free_gb = shutil.disk_usage("/").free / 1024 / 1024 / 1024
if free_gb < MIN_FREE_GB:
    print(f"мало места: свободно {free_gb:.1f} ГБ")
    sys.exit(1)

print(f"место в порядке: свободно {free_gb:.1f} ГБ")
Разбор по частям: os.path.exists - есть ли файл, os.path.getsize - размер в байтах (делим трижды, чтобы получить мегабайты), shutil.disk_usage - сведения о диске, sys.exit(1) - выйти с кодом ошибки. Запись f"... {переменная}" называется f-строкой: значения подставляются прямо в текст, а :.1f - округлить до одного знака после точки. Имена заглавными буквами (BACKUP) - договорённость: «это настройка, её меняют в одном месте сверху файла».
Задание. В варианте ниже автор спешил и сделал две ошибки - одну логическую и одну синтаксическую. Найди обе, не запуская код. 
import os

if os.path.exists("/home/user/backups/demo-bank.sql")
    print("бэкап есть")
print("бэкапа нет")
Подсказка 1Посмотри на самый конец строки с if. Чего там не хватает по сравнению со всеми примерами выше?
Подсказка 2Теперь посмотри на отступы у двух print. Второй находится внутри условия или снаружи?
Показать разборСинтаксическая: после условия нет двоеточия - if ...:. Логическая: второй print стоит без отступа, то есть не входит в условие и выполнится всегда - скрипт напечатает «бэкапа нет» даже тогда, когда бэкап есть. Правильно так: 
import os

if os.path.exists("/home/user/backups/demo-bank.sql"):
    print("бэкап есть")
else:
    print("бэкапа нет")
