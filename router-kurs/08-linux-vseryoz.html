Linux и терминал всерьёз (через WSL2)

В главе 1 мы только заглянули в терминал. Теперь - по-настоящему, потому что сервер Демо Банка и практически вся индустрия живут на Linux, а не на Windows.

Где это запускать. WSL2 мы уже поставили в главе 6 (wsl --install) - открой то же самое приложение Ubuntu из меню "Пуск", в котором мы проверяли версии git и Docker. Все команды этой главы - в нём, а не в PowerShell: PowerShell - терминал Windows, у него другие команды.
Как работает тренажёр ниже. Это имитация: она понимает ровно те команды, что даны в заданиях, и печатает заранее заготовленный, но правдоподобный вывод - примерно такой же, какой ты увидишь в настоящей Ubuntu. Наберёшь что-то другое - тренажёр не сломался, просто в этом шаге отрабатывается конкретная команда.
Честная оговорка про упрощения. Дальше в курсе будет сервер Демо Банка, и в учебном виде мы почти всегда работаем как единственный человек на машине: один пользователь, одна служба, логи смотрим глазами. В реальном продакшене на одном сервере обычно живут несколько клиентов или несколько окружений, у каждого - свой отдельный пользователь и строго ограниченные права, логи уезжают в отдельную систему сбора, а руками в файлы никто не лазит. Поэтому команды вроде sudo nano /etc/..., которые здесь выглядят обыденно, в настоящей эксплуатации делаются не вручную. Про это будет отдельная глава; сейчас важно понять сами механизмы.

1. Файловая система: одно дерево от корня

Теория. В Windows ты привык к дискам: C:\, D:\ - несколько отдельных "корней". В Linux дисков-букв нет вообще. Есть один корень, он обозначается косой чертой /, и всё остальное - ветки одного дерева. Флешку или второй диск не "открывают как диск E:", а монтируют - подключают в какую-то папку внутри этого дерева, например в /mnt/usb, и дальше работают с ней как с обычной папкой. Важные ветки, которые встретятся в курсе постоянно: /home - домашние папки пользователей (твои личные файлы, аналог C:\Users), /etc - настройки программ (текстовые файлы конфигурации), /var - изменяющиеся данные, в частности логи в /var/log, /usr - сами установленные программы, /tmp - временные файлы, которые никто не обещает сохранить.

Пример. Путь /home/anton/проект/app.py читается справа налево так: файл app.py лежит в папке проект, которая лежит в домашней папке пользователя anton, которая лежит в /home, а та - прямо в корне. Никакой буквы диска в начале нет и быть не может. Кстати, в WSL2 твой диск C: тоже виден - он смонтирован в /mnt/c, ровно по тому же принципу.

Разобранный пример. Команда ls / печатает содержимое корня - список тех самых верхних папок. Команда pwd (print working directory) печатает, где ты сейчас находишься.

$
Задание. Введи по очереди: pwd, затем ls /, затем ls /var/log.
ПодсказкаПосле ls ставится пробел и путь. Одна косая черта - это и есть "самый верх", корень.
Показать разборpwd показал /home/anton - ты стоишь в своей домашней папке, это место по умолчанию при открытии терминала. ls / показал верхние ветки дерева. ls /var/log показал файлы логов - туда мы ещё вернёмся в главе про падения.
Проверь себя. В какой папке логичнее искать файл настроек веб-сервера, а в какой - его логи?
ОтветНастройки - в /etc (например, /etc/nginx/nginx.conf), логи - в /var/log (например, /var/log/nginx/error.log).

2. Права доступа: кто вообще может трогать этот файл

Теория. У каждого файла в Linux есть владелец (конкретный пользователь) и группа (набор пользователей), и три набора разрешений: для владельца, для группы и для всех остальных. Разрешений три вида: r - read, читать; w - write, изменять и удалять; x - execute, запускать (для папки x означает "можно в неё зайти"). Команда ls -l печатает это слева строкой вида -rw-r--r--: первый символ - тип (- файл, d папка), дальше три тройки. Зачем это нужно: чтобы один пользователь (или взломанная программа, работающая от его имени) не мог случайно или намеренно испортить файлы другого пользователя и файлы системы. Менять разрешения - chmod, менять владельца - chown.

Пример. Строка -rwxr-x--- 1 anton demobank 2048 ... deploy.sh читается так: обычный файл; владелец anton может читать, менять и запускать (rwx); участники группы demobank - читать и запускать, но не менять (r-x); все остальные - ничего (---). Команда chmod +x deploy.sh добавляет право запуска, chmod 600 secret.env оставляет чтение и запись только владельцу, а sudo chown anton:demobank deploy.sh назначает владельца и группу.
$
Задание. Введи ls -l, потом chmod +x deploy.sh, потом снова ls -l и найди, что изменилось в первой колонке.
ПодсказкаСмотри на буквы x в строке напротив deploy.sh.
Показать разборБыло -rw-r--r-- - файл можно только читать и (владельцу) менять, запустить нельзя. Стало -rwxr-xr-x - появилось право запуска. Сама chmod ничего не печатает в ответ: в Linux "молча" значит "получилось".
Проверь себя. Файл с паролями к базе Демо Банка имеет права -rw-r--r--. Что здесь плохо?
ОтветЕго может прочитать любой пользователь системы (последняя тройка r--) и любая программа, работающая от их имени. Правильно - chmod 600, то есть -rw-------: доступ только владельцу.

3. sudo: почему "нельзя" - это фича, а не помеха

Теория. Обычный пользователь по умолчанию не может менять файлы в /etc, устанавливать программы и останавливать службы - у него просто нет прав на запись в системные папки. Чтобы выполнить одну команду с правами администратора (в Linux администратора зовут root), её пишут с приставкой sudo: sudo systemctl restart nginx. Система спросит твой пароль. Смысл: администраторские права включаются на одну конкретную команду, а не на всю сессию, поэтому опечатка в обычной работе не может снести систему. В Windows 11 ближайший аналог - окно "Разрешить приложению внести изменения?", только в Linux это встроено прямо в командную строку и видно в истории команд.

Пример. Попытка записать в системный файл без sudo заканчивается отказом: bash: /etc/hosts: Permission denied. Это не поломка и не повод "дать себе права на всё" - это сигнал остановиться и подумать: точно ли я должен править системный файл, и что именно я меняю. Привычка работать под root постоянно - главная причина историй "я одной командой удалил сервер".
$
Задание. Сначала whoami, затем echo test > /etc/hosts (получишь отказ), затем sudo whoami.
Подсказкаwhoami печатает имя текущего пользователя. Добавь перед ней sudo и посмотри, что изменится.
Показать разборБез sudo ты anton и в /etc писать не можешь - Permission denied. С sudo та же команда отвечает root: на время одной команды ты администратор. Именно это ограничение и не даёт обычной ошибке превратиться в аварию.

4. Процессы: ps aux и kill

Теория. Процесс - это запущенный экземпляр программы. Один и тот же браузер, запущенный дважды, - два процесса. У каждого процесса есть номер, PID (process id), и владелец - пользователь, от имени которого он работает (а значит, и права из шага 2). Команда ps aux печатает список всех процессов в системе: кто владелец, какой PID, сколько процессора и памяти занимает, и какой командой запущен. Чтобы попросить процесс завершиться, используют kill PID - это мягкое завершение: процессу отправляется сигнал "пожалуйста, закройся", и он успевает сохранить данные и корректно закрыть файлы. Если процесс завис и на просьбу не отвечает, есть kill -9 PID - принудительное убийство: ядро просто прекращает процесс, без всякого "сохранить". Поэтому -9 - последнее средство, а не первое.

Пример. Веб-приложение Демо Банка зависло. Сначала ps aux | grep python - найти PID. Потом kill 8421 - попросить закрыться (у приложения есть шанс дописать незаконченный запрос в базу). Если через несколько секунд процесс всё ещё в списке - kill -9 8421.
$
Задание. Введи ps aux, затем kill 8421, затем снова ps aux.
ПодсказкаPID - вторая колонка вывода ps aux. Ищи строку с app.py.

Проверь себя. Почему не начинать сразу с kill -9, если он "надёжнее"?
ОтветПотому что при -9 программа не получает возможности завершиться аккуратно: незаписанные данные теряются, временные файлы и блокировки остаются. Обычный kill даёт ей закрыться по-человечески.

5. systemd и systemctl: службы, которыми управляют

Теория. В главе 1 было понятие службы - программы, которая работает сама в фоне, без того чтобы её каждый раз открывали. Теперь инструмент: в современных Linux службами управляет systemd, а разговариваем мы с ним командой systemctl. Четыре команды покрывают 90% работы: systemctl status nginx - в каком состоянии служба, systemctl start nginx - запустить сейчас, systemctl stop nginx - остановить, systemctl restart nginx - перезапустить (нужно после правки настроек). Отдельно стоит systemctl enable nginx - "запускать автоматически при загрузке сервера". Enabled и active - разные вещи: служба может быть запущена сейчас, но не включена в автозагрузку, и тогда после перезагрузки сервера она не поднимется. Команды start/stop/restart/enable меняют состояние системы, поэтому требуют sudo.

Пример. В выводе systemctl status самая важная строка - Active:. active (running) - работает. inactive (dead) - остановлена. failed - пыталась запуститься и упала; вот тогда идём читать логи (следующий шаг).
$
Задание. Посмотри состояние: systemctl status nginx. Останови: sudo systemctl stop nginx. Проверь ещё раз status. Подними обратно: sudo systemctl start nginx.
Подсказкаstatus можно смотреть без sudo, а вот stop и start - только с ним.
Показать разборПосле stop строка Active: стала inactive (dead), а строка Loaded: по-прежнему говорит enabled - то есть служба выключена сейчас, но при следующей загрузке машины поднимется снова. После start - опять active (running). Сами start/stop, как и kill, ничего не печатают.

6. journalctl: где искать, что случилось

Теория. systemd собирает весь вывод служб в общий журнал, и читается он командой journalctl. Полезные варианты: journalctl -u nginx - только записи конкретной службы (-u = unit, так systemd называет службу); journalctl -u nginx -n 20 - последние 20 строк; journalctl -u nginx -f - следить в реальном времени, новые строки появляются сами (выход - Ctrl+C); journalctl -u nginx --since "10 min ago" - только за последние 10 минут. Это первое, что делают, когда служба failed или "всё работало и перестало": не угадывать, а прочитать, что система сама написала о проблеме.

Пример. Служба не поднимается. systemctl status говорит только failed, а journalctl -u demobank-api -n 20 показывает конкретную причину - например, что порт уже занят другим процессом или что не найден файл конфигурации. Дальше в курсе есть целая глава "когда всё упало", и она почти полностью про эту команду.
$
Задание. Введи systemctl status demobank-api, увидь failed, а потом выясни причину: journalctl -u demobank-api -n 20.
Подсказка-u - имя службы, -n 20 - сколько последних строк показать.
Показать разборВ журнале прямым текстом написано, что адрес уже используется (Address already in use) - значит, порт 8000 занял другой процесс. Дальше алгоритм: ps aux | grep 8000, найти PID, завершить лишний процесс, снова start. Status говорит "плохо", journalctl говорит "почему".

7. Утилиты для текста: grep, cat, less (и что есть дальше)

Теория. В Linux почти всё - настройки, логи, вывод команд - это текст, поэтому утилиты для текста и есть основной инструмент. cat файл печатает файл целиком - удобно для коротких файлов. less файл открывает файл для просмотра с прокруткой (стрелки, /слово для поиска, q для выхода) - для больших логов только так. grep слово файл печатает только те строки, где встречается это слово: главный инструмент поиска в логах. Полезные ключи: -i - не различать заглавные и строчные, -n - показывать номера строк, -r - искать по всем файлам в папке. Существуют ещё sed (заменить текст по шаблону) и awk (разобрать строку на колонки и посчитать) - для более сложной обработки; их разберём по мере необходимости, запоминать всё сразу не нужно и вредно.

Пример. В логе на 50 000 строк нужны только ошибки: grep -i error /var/log/demobank/app.log. Если ошибок много и они не влезают на экран - grep -i error /var/log/demobank/app.log | less и листать спокойно.
$
Задание. Посмотри файл целиком: cat app.log. Потом оставь только ошибки: grep -i error app.log.
ПодсказкаПорядок аргументов у grep: сначала что ищем, потом где ищем.
Показать разборcat вывалил все строки, включая обычные INFO. grep -i error оставил только строки со словом error в любом регистре - из шума сразу видно два события. Именно так читают логи на практике: не глазами по всему файлу, а фильтром.

8. Пайпы и перенаправления: | > >>

Теория. Идея, на которой держится весь Linux: маленькие команды соединяются в цепочку. Вертикальная черта | (пайп, "труба") берёт то, что напечатала левая команда, и подаёт это правой команде как входные данные - вместо того, чтобы выводить на экран. Знак > перенаправляет вывод в файл, стирая прежнее содержимое файла, а >> - дописывает в конец. Разница между ними стоила людям множества случайно затёртых файлов, так что запомни: одна стрелка - перезаписать, две - дописать.

Пример. ps aux | grep app.py - вывод длинного списка процессов не попадает на экран, а уходит в grep, и на экран печатаются только строки про app.py. Ещё примеры: journalctl -u demobank-api | grep -i error - только ошибки службы; ps aux | wc -l - просто посчитать количество строк (wc -l считает строки); echo "начало работ" >> ~/deploy.log - дописать пометку в свой журнал действий.
$
Задание. Найди процесс приложения не глазами, а фильтром: ps aux | grep app.py. Потом посчитай, сколько всего процессов: ps aux | wc -l.
ПодсказкаПайп ставится между двумя командами, с пробелами по краям: команда1 | команда2.
Показать разборВ выводе видно две строки: сам процесс app.py и заодно строка с самой командой grep - grep находит и себя, потому что его собственная командная строка содержит искомое слово. Это нормально и встречается у всех; PID нужного процесса берём из первой строки. wc -l вернул одно число - количество строк, то есть примерно количество процессов (плюс строка заголовка).
Проверь себя. Ты весь день дописывал заметки в ~/deploy.log и по привычке набрал echo "готово" > ~/deploy.log. Что произошло с прежними заметками?
ОтветОни стёрты: одна стрелка перезаписывает файл целиком. Нужно было >>. Восстановить нечем - корзины у перенаправления нет.

  • прочитать строку -rwxr-x---: кто что может делать с этим файлом
  • сказать, зачем нужен sudo и почему запрет на запись в /etc - это защита, а не помеха
  • найти процесс через ps aux и объяснить разницу между kill и kill -9
  • управлять службой через systemctl status/start/stop/restart и объяснить, чем active отличается от enabled

  • отфильтровать лог через grep и объяснить, что делают |, > и >>
