База данных: миграции, бэкап и восстановление

Где Демо Банк хранит счёта и операции, и что делать, чтобы это хранилище не потерялось вместе с ноутбуком.

Как работает тренажёр ниже. Это имитация терминала: он понимает ровно те команды, что даны в заданиях этой главы, и печатает тот ответ, который в реальности печатает настоящая программа. Если ответа нет вовсе - так и написано словами: «команда ничего не выводит». Наберёшь что-то другое - тренажёр не сломался, просто в этом шаге отрабатывается конкретная команда.
Честная оговорка про упрощение. Всё, что ниже - одна база данных на одной машине, пароль прямо в команде запуска, бэкап в файл рядом. В реальном проде, где на одном сервере живут данные многих клиентов, так не делают: там пароли лежат в хранилище секретов, бэкапы уходят в отдельное хранилище по расписанию, у базы есть реплика (вторая копия, которая непрерывно повторяет за основной), а доступ разграничен по пользователям. Мы осознанно строим учебный вариант - но называем это учебным вариантом, а не «так и надо».

Что такое реляционная база данных

Теория. Реляционная база данных - это набор таблиц: у каждой таблицы есть столбцы (что именно мы храним: номер счёта, баланс) и строки (по одной на каждый счёт). Очень похоже на несколько листов Excel, но с одним важным отличием: таблицы официально связаны между собой. В таблице карт есть столбец «к какому счёту относится эта карта», и база сама следит, чтобы там не оказалось номера счёта, которого не существует. Такое правило называется ограничение целостности. Плюс база умеет принимать много запросов одновременно и не путаться: два перевода, пришедшие в одну секунду, не перезапишут друг друга.

Пример. Если хранить счёта Демо Банка в текстовом файле accounts.txt, то при двух одновременных переводах две программы одновременно прочитают файл, обе посчитают баланс от старого значения и обе его перезапишут - одна операция просто исчезнет. А ещё ничто не помешает записать операцию на счёт №777, которого в файле нет. База данных обе эти беды закрывает встроенно: первую - транзакциями (операция или проходит целиком, или не проходит вовсе), вторую - связями между таблицами.
Проверь себя. Почему для Демо Банка «просто файл с данными» - плохая идея, даже если данных мало?
ОтветПотому что файл не умеет ни безопасно принимать одновременные изменения, ни проверять, что деньги списывают со существующего счёта. Проблема не в объёме данных, а в одновременном доступе и целостности.

Запускаем PostgreSQL контейнером

Теория. PostgreSQL - это СУБД, то есть программа-сервер, которая хранит базы данных и отвечает на запросы к ним. Ставить её на Windows вручную не обязательно: проще запустить готовый образ в Docker (про Docker уже был разговор в главе 6, подробный разбор - в следующей главе). В команде запуска важны три вещи: -e POSTGRES_PASSWORD=... задаёт пароль администратора базы (без него образ postgres откажется стартовать), -p 5432:5432 пробрасывает порт наружу, чтобы к базе можно было подключиться со своей машины, а -d означает «запусти в фоне и верни управление».

Пример. Полная команда: 
docker run --name demobank-db -e POSTGRES_PASSWORD=secret -p 5432:5432 -d postgres
В ответ Docker печатает длинную строку из цифр и букв - это идентификатор созданного контейнера, и больше ничего. Это и есть признак успеха: ошибок нет.
$
Задание. Запусти базу: docker run --name demobank-db -e POSTGRES_PASSWORD=secret -p 5432:5432 -d postgres, затем проверь, что контейнер жив: docker ps
ПодсказкаКоманду можно скопировать целиком. docker ps показывает только работающие контейнеры - если там пусто, контейнер упал.
Показать разборПервая команда вернула идентификатор контейнера - значит, он создан и запущен в фоне. docker ps показал строку с образом postgres, статусом Up и проброшенным портом 0.0.0.0:5432->5432/tcp. Теперь на порту 5432 твоей машины слушает настоящий PostgreSQL.

Подключение и создание базы для Демо Банка

Теория. psql - это консольный клиент PostgreSQL: программа, через которую человек пишет запросы к базе. Он уже лежит внутри контейнера, поэтому вызываем его через docker exec (выполнить команду внутри работающего контейнера). Флаг -U postgres - под каким пользователем базы подключаемся, -c "..." - выполнить один запрос и выйти. Одна СУБД может держать много отдельных баз, поэтому для проекта создаём свою: demobank.

Пример. На CREATE DATABASE demobank; PostgreSQL отвечает ровно одним словом - CREATE DATABASE. Это не эхо твоей команды, а стандартный ответ сервера «команда такого типа выполнена». У каждой SQL-команды такой ответ свой: CREATE TABLE, INSERT 0 1 и так далее.
$
Задание. Создай базу: docker exec -it demobank-db psql -U postgres -c "CREATE DATABASE demobank", потом посмотри список баз: docker exec -it demobank-db psql -U postgres -l
ПодсказкаКавычки вокруг SQL-запроса обязательны, иначе оболочка разорвёт его по пробелам.
Показать разборПервая команда ответила CREATE DATABASE. Вторая напечатала таблицу баз: demobank, postgres и две служебные template0/template1 - они есть в любом свежем PostgreSQL, это шаблоны, из которых копируются новые базы.

Три таблицы Демо Банка

Теория. Схема - это описание того, какие таблицы есть и что в них за столбцы. Делаем минимум, достаточный для демонстрации: accounts (счета), cards (карты) и transactions (операции). SERIAL PRIMARY KEY - столбец с автоматически растущим номером, уникальным для строки: по нему на строку можно ссылаться. REFERENCES accounts(id) - и есть та самая связь: база не даст вставить карту с номером счёта, которого нет. NUMERIC(14,2) - число с ровно двумя знаками после запятой; для денег берут именно его, а не «дробное число вообще», чтобы копейки не плыли при округлении.

Пример. Готовый SQL: 
CREATE TABLE accounts (
  id SERIAL PRIMARY KEY,
  number TEXT UNIQUE NOT NULL,
  balance NUMERIC(14,2) NOT NULL DEFAULT 0
);

CREATE TABLE cards (
  id SERIAL PRIMARY KEY,
  number TEXT UNIQUE NOT NULL,
  account_id INTEGER NOT NULL REFERENCES accounts(id)
);

CREATE TABLE transactions (
  id SERIAL PRIMARY KEY,
  from_account INTEGER REFERENCES accounts(id),
  to_account INTEGER REFERENCES accounts(id),
  amount NUMERIC(14,2) NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT now()
);
На каждую такую команду psql отвечает CREATE TABLE - и ничего больше.
$
Задание. Создай таблицу счетов одной командой: docker exec -it demobank-db psql -U postgres -d demobank -c "CREATE TABLE accounts (id SERIAL PRIMARY KEY, number TEXT UNIQUE NOT NULL, balance NUMERIC(14,2) NOT NULL DEFAULT 0)", затем попробуй нарушить целостность: docker exec -it demobank-db psql -U postgres -d demobank -c "INSERT INTO cards (number, account_id) VALUES ('4111', 777)"
ПодсказкаФлаг -d demobank говорит, в какой именно базе выполнять запрос. Без него попадёшь в базу postgres.
Показать разборПервая команда ответила CREATE TABLE. Вторая - ошибкой: база отказалась вставить карту, привязанную к несуществующему счёту №777, потому что такого id в accounts нет. Это и есть проверка целостности в действии - в текстовом файле такая запись прошла бы молча.

Миграции: изменения структуры файлами, а не руками

Теория. Миграция - это файл с SQL-изменениями структуры базы, у которого есть номер: 001_create_accounts.sql, 002_add_cards.sql, 003_add_currency.sql. Инструмент миграций (их много: Flyway, Liquibase, golang-migrate, Alembic) хранит в самой базе табличку «какие номера уже применены» и применяет только новые, строго по порядку. Суть не в удобстве, а в повторяемости: те же самые изменения, что ты применил у себя, автоматически применятся на тестовом и на боевом сервере - и не надо вспоминать по памяти, «что я там менял руками две недели назад».

Пример. Понадобилось хранить валюту счёта. Ты не заходишь в базу и не правишь таблицу вручную, а создаёшь файл 003_add_currency.sql со строкой ALTER TABLE accounts ADD COLUMN currency TEXT NOT NULL DEFAULT 'RUB';, кладёшь его в папку migrations/ и коммитишь в git. На сервере при следующем развёртывании миграция применится сама - и структура базы там станет ровно такой же, как у тебя. Ответ базы на такую команду - ALTER TABLE.
$
Задание. Примени «миграцию» вручную, чтобы увидеть, что внутри неё ничего магического: docker exec -it demobank-db psql -U postgres -d demobank -c "ALTER TABLE accounts ADD COLUMN currency TEXT NOT NULL DEFAULT 'RUB'"
ПодсказкаМиграция - это просто SQL в файле. Здесь мы выполняем тот же SQL напрямую, чтобы понять, что именно делает инструмент миграций.
Показать разборОтвет - ALTER TABLE. Разница между этим и настоящей миграцией не в SQL, а в том, что при миграции этот SQL лежит в версионируемом файле с номером, и база помнит, что номер 003 уже применён - значит, второй раз он не выполнится и на сервере результат будет тот же.
Проверь себя. Ты добавил столбец руками у себя на ноутбуке, а на сервере забыл. Что сломается и как миграции это предотвращают?
ОтветКод, который ждёт столбец currency, на сервере упадёт с ошибкой «столбца не существует». Миграции предотвращают это тем, что изменение лежит в файле в репозитории и применяется на каждой машине одинаково и автоматически.

Бэкап: pg_dump

Теория. pg_dump - штатная утилита PostgreSQL, которая выгружает базу в файл: по умолчанию это обычный текст с SQL-командами, которые заново создадут таблицы и вставят все строки. Знак > в команде - перенаправление: то, что программа напечатала бы на экран, уходит в файл. Важная деталь: при успехе pg_dump не печатает ничего - ни «готово», ни процентов. Молчание и есть успех; убедиться можно, посмотрев, что файл появился и не пустой.

Пример. docker exec demobank-db pg_dump -U postgres demobank > backup.sql - и приглашение терминала просто возвращается. Дальше ls -lh backup.sql покажет размер файла, а head -3 backup.sql - первые строки дампа со служебными комментариями PostgreSQL.
Бэкап, который ни разу не восстанавливали, - это не бэкап, а иллюзия бэкапа. Файл может быть обрезан, сделан не с той базы, зашифрован ключом, который потерян, - и выяснится это ровно в тот момент, когда он нужен. Поэтому следующий шаг главы - не «сделали дамп», а «восстановили из дампа и проверили данные».
$
Задание. Сделай бэкап и убедись, что файл не пустой: docker exec demobank-db pg_dump -U postgres demobank > backup.sql, затем ls -lh backup.sql и head -3 backup.sql
ПодсказкаЕсли после первой команды ничего не напечаталось - всё правильно. Проверяй результат не по выводу, а по файлу.
Показать разборpg_dump промолчал, ls -lh показал файл размером несколько килобайт, head - шапку дампа (-- PostgreSQL database dump). Три признака вместе означают, что файл реально создан и содержит SQL, а не пустоту из-за ошибки.

Восстановление: главное упражнение главы

Теория. Текстовый дамп восстанавливают, «скормив» его psql: psql < backup.sql - клиент просто выполняет команды из файла одну за другой, поэтому в выводе бегут строки CREATE TABLE, COPY 2, ALTER TABLE. Дампы в бинарном формате (сделанные с ключом -Fc) восстанавливают другой утилитой - pg_restore. Восстанавливать надо в пустую базу: сначала удалить сломанную (DROP DATABASE), потом создать заново (CREATE DATABASE), потом залить дамп.

Пример. Полный цикл «база сломалась»: 
docker exec -it demobank-db psql -U postgres -c "DROP DATABASE demobank"
docker exec -it demobank-db psql -U postgres -c "CREATE DATABASE demobank"
docker exec -i demobank-db psql -U postgres -d demobank < backup.sql
docker exec -it demobank-db psql -U postgres -d demobank -c "SELECT count(*) FROM accounts"
Последняя команда - и есть проверка: если число строк совпало с тем, что было до аварии, бэкап рабочий.
$
Задание (обязательное). Проведи учебную аварию и восстановление по шагам:
1) docker exec -it demobank-db psql -U postgres -c "DROP DATABASE demobank"
2) docker exec -it demobank-db psql -U postgres -c "CREATE DATABASE demobank"
3) docker exec -i demobank-db psql -U postgres -d demobank < backup.sql
4) docker exec -it demobank-db psql -U postgres -d demobank -c "SELECT count(*) FROM accounts"
ПодсказкаНа шаге 3 флаг -i (а не -it) обязателен: он оставляет открытым вход, через который в контейнер льётся содержимое файла.
Подсказка 2Если DROP DATABASE ругается, что база используется - закрой открытые к ней сессии psql; PostgreSQL не удаляет базу, к которой кто-то подключён.
Показать разборШаг 1 ответил DROP DATABASE - данных больше нет, авария смоделирована. Шаг 2 - CREATE DATABASE, пустая база готова. Шаг 3 напечатал поток ответов (SET, CREATE TABLE, COPY 2, ALTER TABLE) - это psql выполнял команды из файла. Шаг 4 показал count = 2, столько же счетов, сколько было до удаления. Вот теперь бэкап проверен - до шага 4 он был только предположением.
Проверь себя. Ты восстановил базу и psql не выдал ни одной ошибки. Достаточно ли этого, чтобы считать бэкап проверенным?
ОтветНет. Отсутствие ошибок говорит только о том, что SQL выполнился. Проверка - это сравнение данных: сколько строк в таблицах, есть ли нужные счета и операции. Дамп полусуточной давности тоже восстановится без ошибок, но потеряет всё, что было после.

  • создать базу demobank и таблицу в ней через psql -c, зная, что в ответ придёт CREATE DATABASE / CREATE TABLE
